# 1차 선별 기준

논문(또는 특허)이 **{프로젝트의 문제}에 활용 가능한가**를 초록만 보고 **포함(in) / 제외(out)** 둘 중 하나로 판정한다.

> 괄호 안 자리표시는 paper-screen 스킬이 프로파일(`docs/profile/overview.md`의 문제 정의, `techniques.md`의 보유 기법)로 채운 뒤 사용자 검토로 확정한다. 확정 뒤 이 안내 줄은 지운다.

## 대원칙

"{프로젝트의 문제}에 직접 쓰인 논문"이 아니어도 **기법을 떼어내 {프로젝트의 부품 사슬. 예: 설계 → 알고리즘 → 구현}에 이식할 수 있으면 포함**한다. 응용 분야가 달라도 이식 가능한 기법이 있으면 포함한다.

판정의 축은 "어느 분야냐"가 아니라 **"{프로젝트}에 새로 이식할 기법이 있나"**다. 표준 기법을 그대로 갖다 쓴 수준이면 분야 불문 제외한다. 이미 가진 기법(`techniques.md`)의 반복이면 제외한다.

## 포함 (in)

- **A. 직접 관련**: {프로젝트의 문제나 제품을 직접 다룸}
- **B. 같은 계열 일반**: {같은 계열의 문제. 예: 같은 종류의 저장 장치, 같은 종류의 신호}
- **C. 이식 가능 알고리즘**: {핵심 알고리즘의 변형과 개선}
- **D. 이식 가능 구현**: {하드웨어나 소프트웨어 구현 구조, 병렬화, 메모리}
- **E. 이식 가능 설계**: {입력 구조나 부호나 모델의 설계 방법}

## 제외 (out)

- **{프로젝트가 다루지 않는 변종}**: (예: 이진이 아닌 부호, 다른 부호 계열)
- **표준 기법의 단순 재사용**: 새 기여 없이 표준 구성만 쓴 것
- **서베이와 리뷰**: 구체적 신규 기여나 정량 비교가 없으면 제외
- **순수 이론 한계(bound)**: 알고리즘, 구현, 설계로 이어지지 않는 것
- **부수 언급**: {프로젝트의 기법}이 베이스라인으로만 나오고 떼어낼 것이 없는 것
- **{이식성이 약한 구현 방식}**: (예: 아날로그 회로 구현)
- **{문제 정의가 다른 것}**: (예: 파라미터를 모르는 상태에서 추정하는 문제)

## 판단 절차

- 1. 초록에서 **떼어낼 수 있는 기법**(알고리즘, 구현, 설계)을 먼저 찾는다
- 2. 그 기법이 포함 갈래에 들면 포함
- 3. 제외 갈래에 들면 제외
- 4. 둘 다 아니면 제외
- 5. 애매하면 포함으로 살리되 reason에 근거를 남긴다 (전문 분석에서 다시 본다)

## 출력 형식

```json
[{"id": "...", "decision": "in|out", "reason": "한 줄 근거"}]
```

기준을 바꿀 만한 것이 보이면 판정과 별개로 `criteria_suggestions` 목록에 문장으로 적는다. 기준서는 사용자가 고친다.
