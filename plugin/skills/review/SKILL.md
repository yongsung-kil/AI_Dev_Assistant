# 리뷰 (관점 도출, 분석, 검증)

- ㉮ 딥 리뷰(기본): 1라운드 → 2라운드 → 3라운드. 2라운드 결과에 검증할 것이 없으면 라이트로 전환해 끝낸다
- ㉯ 라이트 리뷰: 1라운드 + 2라운드에서 끝낸다
- ㉰ 자동 진행: 라운드 사이에 사용자에게 묻지 않는다. lv, 작업자 수, 3라운드 진행 여부는 메인이 정하고 바로 다음으로 간다. 라운드 보고는 파일에만 적고, 사용자 보고는 끝에 한 번 한다

작업자는 `ai-assisted-dev:reviewer`(읽기 전용, git diff 허용). 파일 저장은 메인이 한다. 기록 위치는 진행 중인 작업이 있으면 `_pm/tasks/{작업}/review/`, 없으면 `_pm/tasks/{YYYYMMDD}_review/`. pm 스킬로 TODO에 등록한다.

## 라운드 폴더

`review/r{N}_{round}_{lv}_{이름}/`. N은 자동 증가, round는 round1|round2|round3, lv는 lv1|lv2, 이름은 목적 (perspectives, analysis, verification, breadth2). 예: `r1_round1_lv1_perspectives/`, `r2_round2_lv1_analysis/`, `r3_round3_lv2_verification/`.

## 구조 (lv)

- ㉮ lv1: 메인이 작업자 N명에게 직접 배정. 빠르고 단순
- ㉯ lv2: 메인이 팀 리더 역할을 맡아 팀마다 워커 2~3명의 관점을 정해 부르고, 팀 안에서 교차 분석한 요약을 만든다 (작업자는 작업자를 부르지 못하므로 팀 리더는 메인이다)

| 라운드 | lv | 이유 |
|---|---|---|
| 1 관점 도출 | 항상 lv1 | 브레인스토밍은 평평한 구조가 맞다 |
| 2 분석 | lv1 또는 lv2 | 규모와 복잡도를 보고 메인이 정한다 |
| 3 검증 | 항상 lv2 | 검증 설계(메인)와 검증 실행(워커)을 나눈다 |

## 심각도

| 심각도 | 정의 | 처리 |
|---|---|---|
| CRITICAL | 멈춤이나 되돌릴 수 없는 손상 | 즉시 수정 |
| HIGH | 틀린 결과를 내지만 계속 돎 | 수정 권고 |
| MEDIUM | 경계 조건 위험, 누락 | 검토 뒤 판단 |
| LOW | 개선 제안 | 참고 |

## 관점 도출 규칙

맥락 우선(고정 역할 없음), 중복 금지, 위험 요소를 빠짐없이, "코드 리뷰" 같은 추상 관점 대신 구체 확인 항목. 관점 풀:

| 변경 종류 | 관점 후보 |
|---|---|
| 코드 | 로직 정확성(버그, 경계, 형, 오류 처리), 호출 사슬 영향(위아래, 인터페이스, 파이프라인), 요구 충족(범위, 방향 이탈, 누락), 교차 검증(중복과 누락, 독립 시각, 대안) |
| 자료와 내용 | 무결성(값 범위, 형식, 누락 필드), 언어 정합(용어 통일, 문법), 형식과 구조(태그, 인코딩), 완전성(누락 항목, 상호 참조) |
| 문서 | 사실 정확성(코드와 일치, 오래된 정보), 구조 일관성, 누락 절, 상호 참조 |

## 1라운드: 관점 도출 (lv1)

- 1. 메인이 변경 파일, diff, 목적을 파악하고 작업을 등록하고 라운드 폴더를 만든다
- 2. reviewer 작업자 N명(보통 3~4)을 background로 부른다. 각자 독립적으로 "어디를 봐야 하는지"(관점명, 확인 항목, 대상 파일)를 낸다. 문제를 찾지는 않는다. 메인이 `agent_{ID}.md`로 저장한다
- 3. 메인이 관점을 합치고 중복을 지워 `report.md`에 적는다 (표: 관점명, 확인 항목, 대상). 2라운드의 lv와 작업자 수를 정한다

## 2라운드: 분석

- 1. 관점을 작업자에게 배정한다 (관점 수가 많으면 관련 것끼리 묶는다). lv2면 팀으로 묶고 `context.md`(변경 목적, diff 명령, 배정 관점, 기술 맥락)를 쓴다
- 2. reviewer 작업자들을 background로 부른다. 지시: 변경 목적, 관점의 확인 항목, 대상, 관련 계획 문서(있으면). 규칙: 문제 없으면 "문제 없음"과 확인 범위, 문제는 파일:줄, 추측 금지, 스타일 지적 금지. 메인이 `agent_{ID}.md`(lv2면 `worker_{팀}_{N}.md`와 팀 요약 `team_{팀}_summary.md`)로 저장한다
- 3. 발견을 합치고 심각도를 매겨 `report.md`에 적는다 (표: 심각도, 문제, 위치, 지적 작업자. 통과 관점과 확인 범위). 라이트 전환 기준으로 3라운드 진행 여부를 정한다

라이트 전환 기준 (위에서 첫 매칭):

| 2라운드 결과 | 결정 |
|---|---|
| 발견 0건 | 라이트 전환 종료 |
| CRITICAL과 HIGH 0건이고, 남은 발견의 코드 근거가 자명함 | 라이트 전환 종료 |
| CRITICAL과 HIGH 0건이고, lv2로 진행했고, 남은 발견의 처방이 코드 삭제나 동작 변경을 요구하지 않음 | 라이트 전환 종료 (교차 분석이 거짓 양성을 이미 걸렀다) |
| CRITICAL이나 HIGH가 1건 이상, 수정 처방이 붙은 발견, 검증이 필요한 발견(재현 조건 불확실, 작업자 사이 이견, 단독 확정) | 3라운드 진행 |

트리거가 "리뷰 라이트"면 기준과 무관하게 여기서 끝낸다.

## 3라운드: 검증 (lv2)

판정과 행동을 좌우하는 발견만 검증한다 (전수가 아니다). 두 축: 사실 검증(발견이 실제인가, 과장인가)과 처방 검증(고치면 해결되는가, 부작용은 없는가).

| 대상 | 검증 |
|---|---|
| CRITICAL과 HIGH 전건 | 필수 |
| 수정 처방이 붙은 발견 (코드 삭제나 동작 변경이면 특히) | 필수 (처방 자체를 검증) |
| 재현 조건 불확실, 작업자 사이 이견, 단독 확정 | 필수 |
| MEDIUM 이하이고 근거 자명 (검색 확정, 전수 실행 실증) | 생략 (2라운드 요약이 정본) |

- 1. 메인이 검증 대상을 팀으로 배분하고 `context.md`(2라운드 발견 요약, 검증 대상과 처방 원문, 생략 항목, 기술 맥락)를 쓴다
- 2. 메인이 팀 리더로서 발견을 가설로 형식화한다: "X 조건에서 Y 코드가 Z 동작을 해 문제 P가 생긴다", 처방은 "Q를 적용하면 P가 풀리고 새 문제가 없다". 가설이 참이면 확인되어야 할 증거 목록을 만든다
- 3. reviewer 워커에게 증거 확인을 맡긴다 (확인됨 | 미확인 | 반박됨, 파일:줄). 메인이 `worker_{팀}_{N}.md`와 `team_{팀}_verification.md`(가설, 증거 결과, 판정)로 저장한다
- 4. 판정: 확인됨(수정 필요), 부분 확인(추가 분석이나 수정 때 주의), 반박됨(제거). 처방은 처방 유효 | 처방 수정 필요(대안) | 처방 반대(사유). `report.md`에 표(원래 심각도, 문제, 판정, 근거)와 종합 판정
- 5. 팀 여유가 있으면 이전 라운드가 보지 않은 영역을 독립 탐색하는 재탐색 팀 하나를 둔다

## 너비 확장

최종 보고 뒤 사용자가 "관점 추가"나 "더 분석"을 요청하면 그 라운드를 반복한다. 이전 라운드의 탐색 범위(어떤 파일을 봤는지)만 공유하고 결론은 공유하지 않는다 (확증 편향 방지). 지시 문구: "이전 라운드에서 {파일 목록}을 분석했다. 결론은 알려주지 않는다. 같은 파일을 독립적으로 다시 보거나 보지 않은 영역을 탐색하라."

## 최종 보고 (끝에 한 번)

```markdown
## 리뷰 최종 보고 ({딥 | 라이트 | 딥에서 라이트 전환})
### 진행 경과
- 1라운드: 관점 N개
- 2라운드: {lv}, 발견 N건 (CRITICAL n, HIGH n, MEDIUM n, LOW n)
- 3라운드: 확인 N / 반박 N / 부분 N (생략이면 사유)
### 확인된 문제
| # | 심각도 | 문제 | 위치 | 판정 |
### 종합 판정
{커밋 가능 | 수정 필요 | 재설계 필요}와 근거
```

## 규칙

- ㉮ 작업자는 코드를 읽기만 하고, 확인한 것만 보고하고, 스타일 지적을 하지 않고, 문제 없으면 확인 범위를 적는다
- ㉯ 빈 결과는 한 번 다시 돌리고, 그래도 비면 메인이 그 관점을 직접 본다. 작업자 사이 모순은 코드 근거가 있는 쪽
- ㉰ 계획 문서(plan)로 만든 구현을 리뷰할 때는 지시에 계획 경로를 넣어 "설계와 코드 일치"에 집중하고, 계획 검토에서 이미 본 설계 결함은 건너뛴다
- ㉱ 문제를 고친 뒤에는 새 리뷰를 돌린다 (수정 범위에 따라 라이트나 딥)
