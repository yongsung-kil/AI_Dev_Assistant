# 디버그 (병렬 가설 탐색)

```
증상 정리 -> 가설 병렬 탐색(4) -> 취합 -> 진단 교차 검증(4) -> 최종 취합
```

작업자는 `ai-dev-assistant:explorer`(읽기 전용) 4명. 파일 저장은 메인이 한다. 기록 위치는 진행 중인 작업이 있으면 `_pm/tasks/{작업}/debug/`, 없으면 `_pm/tasks/{YYYYMMDD}_debug_{주제}/debug/`. 라운드 폴더는 `debug/r{N}_{이름}/`. pm 스킬로 TODO에 등록한다.

## 1단계: 증상 정리 (메인)

| 항목 | 내용 |
|---|---|
| 현상 | 무엇이 기대와 다른가 (오류 문구, 잘못된 출력, 멈춤) |
| 재현 조건 | 언제 어떻게 생기는가 |
| 시점 | 언제부터인가 (`git log`, `git bisect`) |
| 시도한 것 | 사용자가 이미 확인한 것 |

## 2단계: 가설 병렬 탐색 (explorer 4명, background)

증상에서 독립 가설 넷을 만들어 하나씩 준다. 가설은 겹치지 않게, "X 함수의 Y 분기에서 Z 상태 미처리"처럼 구체적으로, "맞다면 코드에서 A를 보면 B여야 한다"는 예측을 붙여, 층위(코드 로직, 자료와 상태, 환경과 설정, 변경 이력, 의존과 연동)를 나눠 잡는다.

작업자에게 주는 것: 증상, 배정 가설과 예측, 탐색 범위 힌트. 돌아온 보고(가설, 판정, 근거, 추가 발견)를 `debug/r{N}_{이름}/agent_{A..D}.md`에 저장한다.

## 3단계: 취합과 우선순위 (메인)

| 판정 | 뜻 |
|---|---|
| 확인됨 | 코드 근거가 가설을 뒷받침. 근본 원인 후보 |
| 가능성 높음 | 간접 근거만 있음 |
| 기각됨 | 코드 근거가 반박 |
| 미확인 | 범위 밖이거나 근거 부족 |

확인됨, 가능성 높음, 미확인 순으로 정렬해 사용자에게 보인다 (자동 진행이면 바로 4단계). 모두 기각이면 추가 정보를 묻거나 새 가설로 2단계를 한 번 더 돈다.

## 4단계: 진단 교차 검증 (explorer 4명, background)

확인됨과 가능성 높음 가설을 다른 관점에서 의심한다.

| 작업자 | 관점 | 핵심 질문 |
|---|---|---|
| A 반증 | 이 진단을 반박하는 코드 근거가 있는가 |
| B 영향 범위 | 이 원인이 맞다면 다른 곳에도 같은 증상이 있어야 하는가, 있는가 |
| C 수정 방향 | 제안된 수정이 부작용 없이 문제를 푸는가 |
| D 대안 원인 | 같은 증상을 설명하는 아직 안 본 원인이 있는가 |

보고는 `debug/r{N}_{이름}/verify_{A..D}.md`. 확인됨 가설이 없으면 이 단계를 건너뛴다.

## 5단계: 최종 취합 (메인)

`debug/DIAGNOSIS.md`에 저장한다.

```markdown
## 진단 결과
### 근본 원인 (코드 위치와 메커니즘)
### 증거
### 검증 결과 (반증 실패 = 신뢰도 높음)
### 수정 방향 (파일:줄 수준)
### 영향 범위
### 확신도: HIGH | MEDIUM | LOW (근거)
```

확신도 LOW면 추가 조사를 TODO에 등록한다. 반증에 성공해 진단이 뒤집히면 사용자에게 알리고 새 가설로 2단계를 한 번 더 돈다. 사용자에게 보이고 수정 진행 여부를 묻는다 (자동 진행이면 수정으로 넘어간다).

## 작업자에게 주는 지시 (2단계)

```
당신은 독립적인 디버그 탐정입니다. 아래 가설이 맞는지 코드에서 증거를 찾으세요.
증상: {1단계 표}
배정된 가설: {가설과 "맞다면 ~여야 한다" 예측}
탐색 범위: {파일과 모듈 힌트}
규칙: 가설이 맞든 틀리든 확인한 것을 모두 적는다. 추측하지 않는다. 다른 원인 후보를 보면 함께 적는다.
보고 꼴: ## 가설 / ## 판정: 확인됨 | 가능성 높음 | 기각됨 | 미확인 / ## 근거 (파일:줄) / ## 추가 발견
```

## 작업자에게 주는 지시 (4단계)

```
당신은 진단 검증자입니다. 아래 진단이 정확한지 [{관점}] 관점에서 검증하세요. 진단을 의심하는 입장에서 보세요.
증상: {원래 증상} / 현재 진단: {근본 원인과 증거} / 제안된 수정: {요약} / 검증 항목: {구체 항목}
```

## 실패 처리와 후속

- ㉮ 모두 기각이고 재실행 뒤에도 같으면 "추가 정보 필요"와 확인한 범위를 보고한다
- ㉯ 원인이 여럿이면 각각의 수정 방향을 기여도 순으로 적는다
- ㉰ 수정이 단순하면 바로 고치고, 복잡하면 plan 스킬로 계획을 세운다. 수정 뒤 review 스킬로 검증한다
