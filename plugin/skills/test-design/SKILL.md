# 테스트 설계 (병렬 관점 도출)

```
대상 분석 -> 케이스 병렬 도출(4) -> 취합 -> 교차 검증(4) -> 최종 테스트 계획
```

작업자는 `ai-dev-assistant:explorer` 4명. 파일 저장은 메인이 한다. 기록 위치는 진행 중인 작업이 있으면 `_pm/tasks/{작업}/test/`, 없으면 `_pm/tasks/{YYYYMMDD}_test_{주제}/test/`. 라운드 폴더는 `test/r{N}_{이름}/`. pm 스킬로 TODO에 등록한다.

## 1단계: 대상 분석 (메인)

대상 범위(파일, 모듈, 기능), 핵심 로직과 분기점, 기존 테스트와 그 범위, 목적(새 기능 검증 | 리팩토링 안전망 | 버그 재발 방지 | 보강)을 정한다.

## 2단계: 케이스 병렬 도출 (explorer 4명, background)

대상에 맞는 독립 관점 넷을 정해 하나씩 준다. 관점 풀: 정상 경로, 경계값과 빈 값, 오류와 실패 경로(예외, 시간 초과, 권한), 통합과 연동(모듈 사이, 외부 연동, 상태 전이), 회귀 보호, 성능과 부하, 보안(입력 검증, 민감 자료). 케이스는 코드의 분기와 상태와 의존에서 뽑는다 (상상이 아니라 근거). 케이스마다 입력, 기대 결과, 대상 코드 위치. 보고는 `test/r{N}_{이름}/agent_{A..D}.md`.

## 3단계: 취합 (메인)

중복을 지우고 비슷한 것을 합친다. 우선순위: P0 핵심 로직(실패하면 기능이 안 됨), P1 주요 경계(실제로 자주 생김), P2 회귀 보호, P3 보강. 미커버 영역을 적는다. 사용자에게 보인다 (자동 진행이면 바로 4단계).

## 4단계: 교차 검증 (explorer 4명, background)

| 작업자 | 관점 | 핵심 질문 |
|---|---|---|
| A 커버리지 | 코드의 분기와 경로 중 케이스가 덮지 않는 것이 있는가 |
| B 실현 가능성 | 각 케이스를 실제로 돌릴 수 있는가. 모의 객체나 고정 자료가 필요한 것은 |
| C 중복과 효율 | 같은 것을 검증하는 케이스, 더 효율적인 조합 |
| D 우선순위 | P0와 P1이 정말 핵심인가, 빠진 P0급은 없는가 |

보고는 `test/r{N}_{이름}/verify_{A..D}.md`.

## 5단계: 최종 테스트 계획 (메인)

`test/TEST_PLAN.md`에 저장한다.

```markdown
# {대상} 테스트 계획
## 개요 (대상, 목적, 기존 테스트)
## 테스트 케이스
### P0 핵심 검증
| # | 케이스 | 입력 | 기대 결과 | 대상 코드 |
### P1 주요 경계
### P2 회귀 보호
### P3 보강
## 테스트 인프라 (모의 객체, 고정 자료, 환경)
## 미커버 영역 (어려운 부분과 이유)
```

## 작업자에게 주는 지시 (2단계)

```
당신은 독립적인 테스트 설계자입니다. 아래 대상을 [{관점}] 관점에서 분석해 테스트 케이스를 도출하세요.
대상: {범위} / 목적: {목적} / 확인 항목: {목록} / 기존 테스트: {경로 또는 없음}
규칙: 코드를 직접 읽어 분기와 조건과 상태를 파악한 뒤 케이스를 뽑는다. 케이스마다 입력, 기대 결과, 대상 코드 위치를 적는다.
```

## 실패 처리와 후속

- ㉮ 대상이 넓어 표면 케이스만 나오면 모듈별로 나눠 다시 돌린다
- ㉯ 기존 테스트와 겹치면 기존 테스트를 알려 주고 "미커버만 도출"로 다시 돌린다
- ㉰ 계획 확정 뒤 테스트 코드는 일반 작업 규칙(테스트 먼저)으로 구현한다. 설계 중 버그를 보면 debug 스킬로, 설계 결함을 보면 plan 스킬로 넘긴다
