# 계획 수립 (병렬 에이전트 3라운드)

흐름은 고정이다. 병렬 작업자 넷이 재료를 모으고 메인이 취합하는 패턴을 세 번 반복한다.

```
계획(4) -> 취합 -> 검토계획(4) -> 취합 -> 검토(4) -> 최종 취합
```

작업자는 항상 4명. 코드를 읽는 라운드는 `ai-assisted-dev:explorer`(읽기 전용), 문서만 보는 라운드는 일반 에이전트. 파일 저장은 메인이 한다. 결과 문서는 `_pm/tasks/{작업}/{작업}_PLAN.md`이고 취합(2, 4, 6단계)마다 덮어쓴다 (문맥 유실 대비). 작업 폴더가 없으면 pm 스킬로 먼저 등록한다.

## 1단계: 계획 (작업자 4명, background)

과제를 독립된 측면 넷으로 나눠 하나씩 준다. 코드 작업이면 아래 역할을 쓴다.

| 작업자 | 역할 | 출력 |
|---|---|---|
| A 패턴 탐색 | 요청과 가장 비슷한 기존 구현을 찾아 구조(상태, 초기화, 생성, 갱신, 마무리)를 적는다 | 참조 패턴 요약과 파일 목록 |
| B 영향 범위 | 바꿔야 할 모든 위치. 상수와 분기표와 설정 배열, 호출 사슬(진입점부터), 숨은 종속 | 변경 위치 목록 |
| C 제약 수집 | 프로파일 constraints.md, CLAUDE.md 규칙, TODO의 보류 사항 | 제약 점검표 |
| D 대안과 위험 | 다른 셋과 독립된 시각. 기존 테스트와 자료 호환, 성능, 대안 접근 | 대안과 위험 보고 |

문서나 아키텍처 작업이면 측면을 새로 정한다 (현황, 변경 항목, 순서와 의존, 위험).

## 2단계: 취합 (메인)

작업자 결과를 문서 하나로 합친다. 충돌은 코드 근거가 있는 쪽을 택한다. 누락을 보완한다. 사용자에게 보이고 피드백을 기다린다 (자동 진행을 지시받았으면 바로 3단계). 피드백이 새 정보면 메인이 반영하고, 방향 변경이면 해당 작업자를 다시 돌린다.

코드 작업의 취합 문서 꼴:

```markdown
# {기능} 구현 계획
## 1. 개요
## 2. 논리 계획 (동작 정의, 규칙, 경계 조건, 종료 조건. 항목마다 제약 근거)
## 3. 코드 계획 (참조 패턴 기반 구조, 변경 위치 표, 함수와 클래스의 이름과 핵심 로직)
## 4. 논리와 코드 교차 검증 표 (논리 항목 | 코드 구현 | 구현 뒤 확인할 것)
## 5. 잠재 문제 (작업자 결과 충돌, 제약을 채우기 어려운 항목)
```

## 3단계: 검토계획 (일반 에이전트 4명, background)

취합 문서만 보고(코드 탐색 없이) 검토 점검표를 만든다.

| 작업자 | 관점 |
|---|---|
| A 정합성과 스펙 | 스펙 준수, 동작 동등성(리팩토링), 호출 지점 누락 가능성 표시 |
| B 안전성과 파이프라인 | 항목 사이 충돌, 단계 사이 입출력 정합, 적용 순서 의존 |
| C 경계 조건과 회귀 | 경계값, 빈 값, 초기화 안 된 값, 기존 테스트 영향, 상수 일관성 |
| D 실현 가능성과 완전성 | 구현 가능한지, 모호한 곳, 빠진 단계, 미결 결정, 검증 방법 누락 |

## 4단계: 취합 (메인)

점검표를 합치고 중복을 지우고 우선순위를 매긴다. 사용자에게 보이고 피드백을 기다린다 (자동 진행이면 바로 5단계).

## 5단계: 검토 (explorer 4명, background)

점검표로 계획을 실제 코드와 대조한다.

| 작업자 | 관점 | 출력 |
|---|---|---|
| A 정합성 | 스펙 조항과 코드 1:1 대조, 줄 번호 확인, 누락 호출 지점 실제 탐지 | 항목별 OK, 문제 발견, 재설계 필요 |
| B 안전성 | 오류 경로 추적, 파이프라인 호출 사슬, 충돌 항목의 코드 근거 | 심각도별 문제 |
| C 경계와 완전성 | 경계 조건 시뮬레이션, 빠진 단계, 미결 결정 | 보완 항목 |
| D 대안과 회귀 | 대안 대비 장단점, 기존 테스트와 자료 호환 | 최종 권고와 조건부 의견 |

## 6단계: 최종 취합 (메인)

검토 결과를 반영해 계획을 확정한다. 심각도별 처리:

| 심각도 | 정의 | 처리 |
|---|---|---|
| CRITICAL | 멈춤이나 되돌릴 수 없는 손상 | 2단계로 돌아가 고치고 3단계부터 다시 (최대 1회. 두 번째면 사용자에게 알린다) |
| HIGH | 틀린 결과를 내지만 계속 돎, 설계를 막음 | 재설계 뒤 재검토 |
| MEDIUM | 경계 조건 위험, 문서 부정확, 누락 | 구현 때 반영 |
| LOW | 이름, 사소한 문서 | 참고 |

사용자에게 보이고 승인을 기다린다 (자동 진행이면 승인으로 본다). 승인되면 pm 스킬로 TODO에 작업을 등록하고 일반 작업 규칙으로 진행한다.

## 사용자 응답

| 입력 | 뜻 |
|---|---|
| `.` | 승인, 다음 단계 |
| 내용 | 피드백. 반영 뒤 다시 취합 |
| `x` | 계획 중단 |

## 작업자 공통 규칙

- ㉮ 프로젝트 CLAUDE.md와 프로파일을 먼저 읽는다
- ㉯ "검토하세요"가 아니라 "A와 B와 C를 확인하고 판정하세요"처럼 확인 항목을 준다
- ㉰ 작업자는 서로의 결과를 보지 못한다. 충돌은 메인이 푼다
- ㉱ 빈 결과는 한 번 다시 돌리고, 그래도 비면 메인이 직접 한다
- ㉲ 자주 나오는 결함: 누락된 호출 지점(문서에 N곳, 실제는 더 많음), 항목 사이 필드 충돌, 스펙과 코드의 상수 불일치. 프로젝트 고유 결함 유형은 CLAUDE.md나 `_pm/`에서 가져온다
